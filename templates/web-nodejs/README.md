## Adding a database

Pick a binding name that reflects the role in your domain (`payments-db`,
`users-db`, `events-db`), not the technology:

```bash
rda add-service postgresql payments-db
```

This appends a `services[]` entry to `deploy/values.yaml` and flips
`suse-library.postgresql.enabled: true` so the next `tilt up` deploys
the SUSE Application Collection postgres sub-chart and wires the
binding-secret to your app at `/bindings/payments-db/`.

The binding-secret carries the canonical Service Binding Specification
keys: `type`, `provider`, `host`, `port`, `username`, `password`,
`database`. Same shape across postgresql, mariadb, and the other
database types in the catalogue.

## How the example app finds the database

`src/index.js` discovers the binding by **type, not name** — same
convention as Paketo / Spring Cloud Bindings. It iterates
`$SERVICE_BINDING_ROOT` (default `/bindings`), reads each entry's
`type` file, and picks the first one whose type is `postgresql`. Your
binding can be named whatever makes sense for your domain; the example
app finds it as long as `type: postgresql` is on disk.

For multiple postgresql bindings in the same project (e.g. a
read-replica setup), pin a specific one via `DB_BINDING_NAME`:

```yaml
# deploy/values.yaml — under suse-library:
env:
  - name: DB_BINDING_NAME
    value: users-db
```

Without the override, the first matching binding wins.

## Switching to a managed instance

For staging+ where the DB is operator-provisioned (CloudNativePG,
Crossplane, Vault dynamic secrets), set `provisioning: external` on
the service entry and supply the endpoint:

```yaml
# deploy/values.yaml — under suse-library.services:
- binding: payments-db
  type: postgresql
  provisioning: external
  endpoint:
    host: pg-prod.cluster.svc
    port: 5432
    scheme: postgresql
```

The library skips the local sub-chart and writes the endpoint into the
binding-secret. Auth keys (username/password) come from a `Secret`
named `<release>-payments-db-binding` that you provision (Fleet,
ExternalSecrets, etc.) — see `concepts/provisioning.md` in the docs.

## What's inside

- `src/index.js` — Express server. Discovers a postgresql binding by
  type; honours `DB_BINDING_NAME` for multi-DB. Returns service info
  on `/`, health on `/health`, readiness on `/ready`.
- `deploy/Chart.yaml` + `deploy/values.yaml` — Helm chart with
  `suse-library` as a dependency. The library renders the Deployment,
  Service, Ingress (when `ingress.enabled`), and per-service binding
  Secrets from the unified `services[]` DSL.
- `Tiltfile` — inner-loop config. Auto-discovers port-forwards from
  `deploy/values.yaml`; nothing in this file needs to change as you
  add/remove services.
- `Dockerfile` — multi-stage build on SUSE BCI Node.js 22. When the
  SUSE-AppCo buildpacks ship, you can drop this file and switch to
  `pack build`.

## Prerequisite for the local Postgres

The local postgresql sub-chart pulls from
`dp.apps.rancher.io/containers/postgresql` (SUSE Application
Collection). Authenticate once with your AppCo / SUSE Customer Center
credentials before the first `tilt up`:

```bash
docker login dp.apps.rancher.io
```

Without this, the postgres pod gets `ErrImagePull`. Once logged in,
Rancher Desktop / Docker reuses the credentials across rebuilds.

## Troubleshooting

**"no postgresql binding mounted"** in the app log — check that the
service is actually deployed (`kubectl get pod | grep postgresql`)
and the binding-secret exists (`kubectl get secret | grep binding`).
Also worth checking `kubectl describe pod <app>` to confirm the
`/bindings/<binding-name>/` volume is in `Mounts`. The app does NOT
care about the binding name, only that `type` reads `postgresql` —
if `type` is wrong or missing, this is the symptom.

**"password authentication failed for user 'postgres'"** in the
postgres pod — almost always a stale PVC from a previous deploy with
a different password. Delete the PVC (`kubectl delete pvc
data-{{ .Name }}-postgresql-0`) and `tilt up` again to let postgres
re-init with the current password.
